# PRD：双端 Agent 真实服务联调与面试演示验收

版本：1.0；日期：2026-10-18；适用项目：private-domain-store-agent。

本文接续 `prd.md`，明确真实服务联调的交付范围、实现约束和通过标准。已有双端页面及商品交易功能继续使用，不重新开发界面。先完成本文，再实施验收环境、运行链路和测试。

## 1. 要解决的问题

现有代码已实现业务接口、工具循环、推荐、RAG、会话及安全保护，已有模拟模型与 SQLite/内存 Redis 回归。2026-10-14 另有云端模型真实推荐和经营查询记录，但尚缺一个可由他人重复运行的统一验收流程。

本次目标是形成可复现的证据链：真实用户问题 → 真实模型输出工具调用 → 服务端权限/参数校验 → SQLAlchemy 查询 MySQL → 工具结果回传模型 → 真实回答 → Redis 保存上下文。售后问答则必须经过真实 Embedding、Chroma 语义召回和真实模型生成，不能用关键词检索或规则回复替代。

## 2. 完成的定义

代码实现、模拟测试、真实服务验收是三个独立状态。真实模式中 SQLite、内存 Redis、测试向量、模拟模型及 fallback 均不得计为通过。服务未启动、凭据缺失、模型未下载均标记为阻塞；模型调用或业务断言不满足标记为失败；报告不得用跳过用例换取全绿。

验收输出带时间、服务实际类型、模型名、Embedding 名、通过/失败场景及耗时。不得记录密码、API Key、JWT、完整收货资料或环境文件。耗时仅作为本轮观测，不能据此承诺性能指标。

## 3. 角色、场景与数据边界

### 买家

- 搜索商品、咨询说明、精确查询 SKU 库存。
- 热销、预算、浏览偏好及相似推荐，结果只含所在店铺可见商品。
- 查询本人在本店订单，追问“这个订单发货了吗”继承上下文。
- 询问商品养护、平台规则和售后政策，回答有来源。
- 下单、支付、取消等操作仍走交易页面与既有业务接口。

### 商家

- 查询本店全部商品/SKU、低库存、全部订单、经营概览。
- 通过后台维护商品价格、库存、上下架和订单状态；修改后买家查询与助手工具读到相同数据。
- 查自己的店铺，不能指定其他商家的 shop_id，也不能绕过权限访问别店订单。

身份来自认证结果，店铺由服务端解析。模型参数不接受 user_id、shop_id、role。另一用户、另一店铺和不存在订单对买家统一返回未找到，避免泄漏订单是否存在。

## 4. 技术职责与一致性

### SQLAlchemy 与 MySQL

SQLAlchemy 是 ORM/数据库访问层，MySQL 是业务持久化存储，两者不是替代关系。商品、用户、SKU、订单及审计落 MySQL。库存扣减、订单写入、取消返库存沿用数据库事务；AI 工具仅查询，不直接修改业务。

验收必须连接 MySQL，并通过数据库查询核对 API 创建的订单、商品修改及工具审计，而非仅检查 DATABASE_URL 字符串。MySQL 数据卷在 API 重启后仍存在。不得迁移或清空现有本地/线上 SQLite 数据来准备演示。

### Redis

Redis 保存热点商品缓存、会话、浏览偏好和限流计数；MySQL 保持价格、库存和订单事实来源。商品列表先读缓存，未命中读 MySQL 并回填；商品/SKU 变更后清理相关缓存；订单工具直接查数据库，不依赖过期订单缓存。

真实验收先填充缓存，再修改价格/库存/上下架，确认缓存失效、买家列表与工具同步。会话键包含用户和店铺，具备 7 天 TTL；需直接在真实 Redis 读取 TTL、历史和摘要，并验证新 API 进程能恢复同一会话。

开发模式允许 Redis 内存降级；严格验收禁止该降级。Redis 失联后健康/就绪检查必须识别，不得继续显示真实 Redis 正常。生产可用性治理不在本次承诺内。

## 5. 真实 Function Calling

- 默认演示使用 Ollama 的支持工具调用模型；保留现有云端模型适配，但报告标注实际 provider，不能把云端运行说成 Ollama 运行。
- LangChain 提供消息、工具 schema、bind_tools 和 ToolMessage；后端工具调用应用服务函数（与 HTTP 接口共用业务逻辑），不声称工具再次发起内部 HTTP。
- 明确业务意图用现有规则识别与路由；模型提取具体参数并输出工具调用。报告注明规则意图识别，不声称训练过意图分类模型。
- 必须观测真实模型 tool_calls、校验后的工具名、业务结果和最后回答；只出现回答或只返回 mode=llm 不足以证明工具执行。
- 必测商品搜索、SKU 库存、本人订单、预算推荐和商家概览。自然语言问题不能在脚本中绕过模型、直接指定执行工具冒充 Function Calling。
- 单轮工具次数及总步骤有界；空输出、非法工具/参数、超时触发稳定错误或显式 fallback。正向真实模型用例出现 fallback 即不通过。

## 6. 真实 RAG

### 数据与索引

知识材料包括商品说明、平台规则和售后文档。使用现有 Markdown 清洗、规范化、标题分块和重叠切片；块有 source、heading_path 与内容。店铺专属政策必须标注/限制适用范围，不能将南枝手作条款默认为其他店铺承诺。

使用真实 Ollama Embedding 模型，文档和问题使用同一模型及匹配的检索输入格式；向量存 Chroma 持久目录，以 cosine 检索。模型或输入格式变更使用新集合重新索引，不能混用向量。先生成向量再写入，生成失败保留旧索引。

中文场景选型记录：首次使用nomic-embed-text实测时，“退货期限”的首位来源错误；添加官方检索任务前缀和细化段落后仍不能稳定满足原题。因此独立验收改用中文BGE-small-zh-v1.5（Ollama社区GGUF发布quentinz/bge-small-zh-v1.5），保留原题和首位命中要求。兼容原nomic配置，但不把下载完成等同于中文检索达标。

### 问答与证据

响应提供结构化知识来源和检索模式，包含 source、heading_path、召回片段与分数/距离。严格模式检索失败直接判失败，不能静默退回关键词。

至少使用退货时效、定制品例外、商品养护三类问题；自然语言改写后仍应召回目标文档。最终回答由真实聊天模型根据工具结果生成，关键结论与片段一致，不能把命中知识库等同于生成回答已通过。未命中应说明没有充分依据，不能自行承诺退款条件。

## 7. 多轮与摘要

Redis 保存原始最近问答和摘要，摘要与消息共同计入字符预算。明确采用字符预算，不虚称精确 token 计数。摘要器使用统一聊天模型接口，保留需求、商品、订单号、预算和未决问题；模型失败时事实摘要回退须有可观测模式。

验收：先问一个具体订单，再继续对话至触发压缩，确认 Redis 有摘要且总上下文有界；压缩后追问仍指向该订单。重启 API 后使用相同身份/店铺/session_id 继续查询；另一身份同 session_id 无历史。商品库存追问先覆盖既有常见表达，不承诺任意代词都能解析。

## 8. 安全与异常

- 买家 A 查买家 B、店铺 A 查店铺 B 的订单均拒绝；数据库审计记录拒绝/失败，响应不包含他人地址或电话。
- 缺参数和负数 SKU 需明确提示，不执行数据库查询；模型附加身份参数和未知工具拒绝。
- 工具暂时失败仅有限重试，不泄漏异常堆栈、连接字符串或密钥。
- 模型不可达、非法工具输出、Embedding 不可达、Redis 不可达各有自动化故障用例；故障可通过独立测试配置注入，不停止用户既有服务。
- 每用户限流在真实 Redis 中验证并返回 429；模型步骤上限与空输出在确定性单元测试覆盖。真实模型不需要被诱导至每一种错误输出才能证明保护代码有效，但报告区分真实服务故障与模拟故障。

## 9. 环境与可重复执行

新增独立 Compose 项目，使用独立容器、数据库、Redis 库和 Chroma 卷。端口避开现有 8000/3306/6379；MySQL/Redis/Ollama 仅本机绑定。不得自动修改线上配置、部署、Git 分支或已有业务数据。

环境分为“基础服务验收”和“含模型完整验收”：前者验证真实 MySQL/Redis/业务，后者追加真实 Function Calling、Embedding、Chroma 和摘要。两者分别出报告；基础通过不能表述为全部通过。

提供环境示例、启动命令、模型下载命令、就绪检查、验收命令、报告路径和保留数据的停服命令。模型下载可能持续较久，需报告实际进度；资源不足则如实保留阻塞状态。云端凭据仅来自环境或独立本地环境文件，不拷贝到报告。

## 10. 验收用例与简历对应

- A01 后端：真实 MySQL 创建商品/SKU、上下架、买家下单、商家查询；直接核对数据库及权限。
- A02 缓存：真实 Redis 缓存命中与业务修改后失效，列表与数据库一致。
- A03 模型工具：真实模型分别选择搜索/库存/订单/推荐/经营工具，参数有效、数据真实、mode=llm。
- A04 RAG：真实 Embedding 生成文档/问题向量，Chroma 存储/语义召回，模型基于片段回答，来源可追踪。
- A05 会话：真实 Redis 历史/TTL、API重启恢复、跨身份隔离、真实模型摘要及压缩后订单追问。
- A06 安全：跨用户/跨店拒绝、身份参数拒绝、审计脱敏、429限流。
- A07 异常：工具失败重试、缺参数、模型空/非法输出、模型/Embedding/Redis不可达均按设计处理；严格环境不误判成功。

每个用例记录预期、实际、断言及证据。最终交付记录对上述七项逐项标记“实现并实测/实现未实测/失败或阻塞”，不生成虚假性能或准确率数字。

## 11. 实施顺序与范围控制

1. 本文先落盘；检查已有云端模型和基础设施，复用现有业务实现。
2. 增加严格验收模式、真实依赖就绪检查、可追踪的检索和摘要元数据，修复阻碍真实联调的接口差异。
3. 增加隔离 Compose、真实验收脚本和故障/接口回归测试。
4. 启动可用的真实服务，运行基础与完整验收，生成实际报告；如环境阻塞仍完成可独立复跑的实现。
5. 更新 README、交付记录和演示步骤；不改写用户简历为未测得的成果。
