# 后端模块详解

## 一、业务形态与技术选型

这个后端支撑的是"单商家私域电商"：一家店归一个商家，买家通过店铺分享码进店，不能跨店浏览，平台运营方在后台统一治理。三个端——买家店铺、商家后台、平台运营台——读的是同一套商品、规格、订单数据，靠状态字段决定"能不能看见、能不能买"，所以不存在"后台改了买家看不到"这类同步问题。

框架选了 FastAPI，看中三点：依赖注入天然适合"认证、权限、数据库会话"这三层切面；参数校验与序列化共用一套类型定义；自动生成的接口文档能直接当验收依据。数据访问用类型化关系映射而不是拼字符串，关键原因是它既能表达原子更新语句，也能精确控制关联数据的加载方式，避免逐条查询。配置在启动时强类型校验，写错立刻报错而不是运行到一半才炸。

存储分工明确：关系库负责权威事实（商品、价格、库存、订单、权限），缓存负责会话与热点数据，向量库只负责语义索引。三者不互相替代，尤其向量库绝不承担"事实"职责。

## 二、分层与职责边界

只有四个层次，依赖方向单向：接口层只处理请求语义（解析、鉴权、调用、返回），不写业务规则；服务层是唯一碰数据库的地方，金额、库存、状态机、权限范围、缓存失效全在这里；助手编排层只通过服务层的只读查询取数，自己不写查询；测试平台有独立的表、队列与执行器，与业务侧共用工具但不共用数据副本。

两条纪律值得单说：**金额一律用整数的最小货币单位**，只在出入口做一次转换，绝不用浮点做金额运算；**同一张表对两个端输出不同字段视图**，而不是维护两套查询，这样买家不该看到的字段在序列化层就被挡掉。

## 三、数据模型里的关键决策

**订单明细保留下单时的快照。** 明细里冗余了当时的商品名、规格名、单价，所以商家后来改名改价，历史订单仍显示下单时的样子。注意区分：影响金额的用快照，纯展示的（比如商品图）用实时值。

**标签关联存标识，分类却存名称。** 标签是多对多，关联表存标识，所以改标签名挂过的商品自动跟着变；分类是存在商品表里的字符串，改名必须级联改商品。这个不一致带来一个通用教训：同一个概念用两种引用方式，就会有两种一致性负担。

**买家端有商品副本，而且是刻意的。** 三层结构：`products` 是 SPU 表，存名称、分类、图片、状态、销量、限购与对客编号 `spu_id`，是唯一权威；`skus` 存每个规格的价格、库存、图与参数，用 `spu_id` 指向 SPU 主键。商家端与平台端直接读写这两张表，看到的就是实时值。买家端商品展示值只取自 `c_product_views`——一行一个 SPU，把最低价、标签、评分、规格明细打包成一份展示载荷，展示查询不需要关联商品与规格表，也不实时聚合评分。投影同步检查仍读取权威表，下单校价、扣库存仍使用权威表。

代价是投影可能过期，所以同步做了三道：每次目录写操作刷新受影响的 SPU；买家每次读取先比一次内容指纹（状态、规格数、库存合计、价格合计、最高价、更新时间），对不上就地重建那一个 SPU；进程启动整表重建。只比时间戳不够——时间戳在 MySQL 上只到秒，同一秒里改价就看不出来，所以指纹里带了内容聚合。

**草稿是状态，不是表。** 建草稿只是插入一条 `status='draft'` 的 SPU，发布只是改状态，不需要搬数据、不换主键，订单、栏目、标签里已有的引用全部保持有效。买家端宽表完全不投影草稿，所以"忘记过滤草稿"这种失误在结构上不成立。

**店铺营业状态不进投影。** 它留在读路径判断，平台冻结店铺立刻生效，不用等投影刷新。

**唯一约束承担了幂等职责。** 很多"只能有一条"的规则直接用数据库唯一约束表达（同人同规格购物车只有一行、一条订单明细只能评一次、一单只能用一张券、每人每券只领一次）。并发下的重复插入由数据库拒绝，应用层只需把冲突转成业务错误，不必自己在应用层加锁判断。

## 四、认证与权限

**令牌是无状态签名加有状态吊销名单的组合。** 令牌里带用户标识、角色、签发时间、唯一编号与过期时间；解码时**显式限定签名算法并强制要求关键字段存在**——不限定算法会留下伪造空间，不强制过期字段会出现永不过期的令牌。退出登录不是客户端删除，而是把令牌写进吊销名单。两个细节：名单存令牌前两段的哈希而非明文（缓存被读走不等于泄露可用凭证），条目有效期等于令牌剩余有效期（令牌自然过期后条目自动回收，名单不会无限增长）。

一个安全取向必须讲：**吊销名单的存储出故障时，接口要拒绝服务，不能当作"没被吊销"放行。** 否则用户点了退出之后令牌会重新生效。这条路径上的失败必须"失败关闭"，而不是放行。

**身份判定有三层，数据库永远是否决权最大的一方。** 第一层是令牌声称的身份；第二层是外部状态（是否已注销、是否被平台停用、某个时间点前签发的令牌是否已被统一作废）；第三层是数据库里的真实授权状态。第三层里最值得说的是**角色降级**：系统做过"统一账号"改造，注册一律是买家，普通账号不允许自动开店，商家身份需要显式授权记录。因此若有人在令牌里把角色改成商家，服务端会按数据库状态**降级回买家**，"自己改令牌冒充商家"这条路彻底走不通。

**401 与 403 的区分被认真处理**：未证明身份返回 401，身份明确但无权限返回 403。前端据此行为不同——401 清本地凭证并跳登录页，403 只提示无权限而不动凭证，避免"偶发无权限被强制登出"。另有防账号枚举的细节：账号不存在时也做一次等价的密码校验把响应时间抹平，否则能靠延迟差异枚举账号。

## 五、交易链路：并发与正确性

**防超卖靠"判断与扣减在同一条语句里"。** 正确写法是"库存减去指定数量"这个更新带上"库存不少于指定数量"的条件，然后看影响了几行：一行才算成功，零行就是不足。错误写法是"先读出来、判断够不够、再写回去"——两个并发请求会同时判断为够用，把库存扣成负数。这个区别是整个交易系统最要紧的一行。

**限购为什么要加锁，以及为什么必须用当前读。** 限购是"累计已购加本次不超过上限"，且按商品累计、跨规格也算，所以必须先读一个聚合值再判断。这里有个容易漏的数据库细节：在默认快照隔离级别下，普通查询读到事务开始时的快照，**看不到其它事务刚提交的订单**，只有显式加锁的当前读才能看到最新已提交数据。只用普通查询，并发下单能绕过限购。另外**限购必须在预留库存之前校验**，否则被拒绝时库存已经扣掉了。

**订单号不能用计数生成。** 用"当天第几单"作编号，两个请求都未提交时会撞号。改成日期前缀加足够长的随机数，靠唯一约束兜底。这是并发下最容易被写错的标识生成方式。

**优惠券用两阶段状态机。** 状态是"可用、占用、已用"：下单时从可用改占用，支付时改已用，取消或超时退回可用。为什么要中间态？因为跨请求的流程不能靠事务回滚——每个请求自己的提交是独立的。若直接标已用，订单取消后券就废了。两个转换都用条件更新，影响行数为零说明状态已变，从而保证**重复转换幂等**，不会出现"支付之后又被超时任务释放"。

**库存回补是自增而不是覆盖式写**（库存等于库存加数量）。销量累计同理。**只有真正把状态从待支付改成已取消的那一次才回补**，靠影响行数判断，所以重复取消、定时任务重复扫到同一单都不会重复回补。**支付把状态与过期判断合并进同一个条件**，所以定时任务失效、双开标签页、重复点击都不会造成重复支付或过期后仍能支付。

## 六、状态机与超时

订单状态是待支付、已支付、已发货、已完成、已取消，加上待支付超时自动取消。所有状态变更都走条件更新，而不是"读出来判断再写回"。定时任务每分钟扫一次超时未支付的订单，逐单条件更新并回补，最后统一提交；任务里的异常被完全吞掉并记日志，因为它不能把进程带崩，失败也不影响下单与支付。

必须如实说的降级局限：**定时器没起来时接口仍可用，但超时订单不会被自动取消。** 真正的兜底只有一处——支付条件里带了过期判断，过期订单付不了款。代码里有一句日志写"超时订单改由接口触发清理"，但实际没有任何接口做这件事，这种"日志描述了不存在的兜底"是要点名的问题。另外**多进程部署时每个进程都会起一个定时器**，同一批订单被扫多次；因为条件更新加影响行数判断，不会重复回补（幂等），但仍浪费查询。正确做法是拆成独立进程或加分布式锁。

## 七、缓存与降级

业务缓存只有一类：买家端商品列表。键包含店铺与筛选条件，有效期一分钟级，任何商品、规格、店铺写操作后**主动失效**。失效策略是"按前缀整片删除"而非精确删除，这是刻意取舍：一次商品改动可能影响所有筛选组合（商品进出分类、价格变化影响价格排序），精确删除要枚举所有组合，很容易漏。代价是**改一个商品会清掉所有店铺这份缓存**，因为键前缀里没有店铺维度——这个粗糙点值得主动承认。

有个设计细节很有价值：**店铺营业状态检查放在读缓存之前**，所以店铺被平台冻结时立即生效，不依赖缓存失效。对应测试也是这么设计的：先预热缓存，再冻结店铺，然后断言买家侧商品为空。**这说明测的是"缓存不会绕过状态检查"，而不是"缓存被清掉了"。**

同一套缓存组件还承担会话、限流计数、浏览记录、令牌吊销名单、测试任务队列。**降级策略是这里比较有分量的一块**：缓存不可用时（启动连不上或运行中断连）切换到进程内存实现，且每次失败的操作会在内存上自动重放一次，保证请求不失败。代价必须说清：进程内存不跨实例共享，所以多实例部署时会话不共享、限流只在单实例生效、队列与互斥锁会失效。**生产必须用真实缓存，降级只是"别让服务完全挂掉"。**

内存实现必须与真实实现**语义一致**，否则降级之后就测不出问题。一个具体例子：限流计数在真实实现里用一段脚本保证"自增"与"首次设置过期"原子，内存实现也刻意做到只在第一次设置过期、后续自增不刷新——两者窗口行为必须一样，且这个语义有专门测试锁定。连接超时压到一秒级，因为不设超时会拖住所有请求。最后是**严格模式开关**：打开后缓存不可用直接报错、数据库不是目标类型直接报错、不允许任何内存降级。

## 八、平台运营与治理

**平台运营是独立的一张表，而不是用户表里的角色值。** 因为这个身份与"店铺内商家"是正交的：同一个人可以既是某店商家又是平台运营，单值角色表达不了；而且授权与撤销是显式的表操作，可以审计。

治理的生效路径要能说清：平台可以限制店铺营业、停用账号、禁售规格、隐藏评价，这些限制被商品可见性、可购性、领券、助手取数共同引用，所以一处限制多点生效。有一个刻意的边界——**被平台限制营业的店铺，商家不能自己解除**（只有平台能）；禁售规格同理，商家不能编辑、排序、上下架或解禁。

审计分来源：平台对商家的每次写操作要求填写原因且原因真实落库；助手侧每次工具调用单独记一张表，含脱敏参数、成功与否、耗时与失败原因分类。这两类不合并，因为读者不同——平台审计是合规视角，工具审计是"护栏是否在生效"的观测视角。一个可主动说的短板：工具审计参数用白名单（只落结构化参数，自由文本不落库），订单编号只留后几位；这是隐私考虑，代价是"用户问了什么"无法从审计还原。

## 九、部署与发布纪律

两条流水线分工明确。主流水线在推送到主分支时触发：装依赖、跑全量后端测试、对前端脚本做语法检查，全通过才部署。它**不并发**，也不取消正在进行的部署——因为部署走到一半被取消会留下"代码是新的但服务没重启"的中间状态。部署有一个关键纪律：**用版本库归档精确部署"被测试的那个提交"**，而不是同步工作区，因为工作区可能混着未提交的并行改动，"测什么就部署什么"必须靠它保证；传输时只带必要目录，不带本地数据库与上传文件。

服务器侧发布脚本做得比较扎实：只接受特定格式的部署指令；用文件锁串行化；解包到临时目录后先做字节码编译预检（坏代码在停服前就被拒绝）；先装依赖（这一步不停服）；备份运行配置、代码包、整个虚拟环境和数据库；同步代码时排除用户上传目录；启动后轮询就绪探针并要求所有检查项通过；**任何一步失败都由错误陷阱自动回滚代码与虚拟环境并重启**。数据库迁移明确不在自动部署范围内，这是刻意的边界。

测试执行进程与接口服务做了资源隔离：不同虚拟环境、不同系统服务、受限的处理器占比、内存软硬上限、进程数上限、只允许写数据目录的只读文件系统、退出时按进程组整体回收。**这才是"测试跑挂不拖垮线上服务"的真正答案**，而不是靠"测试写得轻一点"。

## 十、性能与已知局限

只有一类读缓存，首页、合集、详情、店铺信息都不缓存。买家端商品列表展示数据直接查宽表，筛选、排序下推到数据库，分页仍对结果切片；最低价与销量是独立列，后续可以补组合索引优化排序。读缓存前会检查主表版本，发现变更就重建相应投影并清缓存。评分聚合只在刷新投影时算一次，不再随每次列表请求重算。运营侧与客服消息有真正的数据库分页，买家端宽表列表目前仍为结果切片。

索引有明显缺口：订单的创建时间、过期时间与状态，以及商品分类，都没有索引。直接影响定时取消超时订单的任务每分钟全表扫描订单，按状态筛选订单也要扫。连接池只配了借出前探活，没有配回收时间与池大小。部分列表接口仍有逐条查询问题（订单列表每单查一次优惠券与明细、待评价列表逐个查订单号、运营后台若干列表逐行取数）。可观测性只有文本日志，没有链路追踪、指标采集、结构化日志——要上生产这三样是第一优先级。

最后是没有的东西：没有迁移框架（靠启动时幂等补列与就地改列名，加列、改名方便，改类型与删约束仍不行）；没有退款、没有已支付订单取消、没有自动确认收货；没有接口级幂等键（只有客服消息与测试运行有）；没有分布式锁与消息队列；没有读写分离、分库分表、二级缓存；没有对象存储；搜索是内存匹配加向量语义检索，没有独立搜索中间件；分页没有统一规范；定时任务在多进程下会重复执行。

这份清单本身值得讲——**主动说清"做到什么程度、哪里没做"，比声称全都做完了可信得多。**
