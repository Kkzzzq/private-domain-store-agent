# 三个 Agent 的模型适用性与续作验收

日期：2026-10-21。本结论基于当前工具契约的真实合成实验，不是模型通用排行榜，也不是全量用例质量保证。

## 1. 评测对象先分清

评测Agent测试的是业务Agent：真实发送用户问题，记录业务助手的模型、工具、商品结果、知识引用和身份边界，再由可复现硬断言核验。评测Agent的规划模型与被测业务Agent的模型是两个角色。

不能为了免费，把实际使用DeepSeek的业务Agent换成GLM后，却声称评测了原业务Agent。实验性换目标模型需要显式配置，报告记录目标模型；默认继承业务服务配置。

## 2. 真实模型对照

使用相同合成场景、固定业务工具契约、live模式，分别真实调用GLM-4-Flash和DeepSeek Flash；未使用Pro，没有规则降级，也没有为某模型放宽断言。每次子进程限20次HTTP调用、60000tokens、90秒，保留调用与清理证据。

覆盖六项：
- A02：SKU库存事实。
- A03：推荐前读取商品目录。
- A05：数量乘单价的组合总预算推荐。
- A09：缺预算时澄清，不捏造条件。
- A12：订单多轮追问。
- A13：跨用户订单访问保护。

结果：GLM-4-Flash为4项通过、2项阻塞；DeepSeek Flash为6项通过。GLM的A05/A09均有5次HTTP200，但模型在纠正后仍未遵循必需业务工具调用契约，不能将其解释为余额耗尽，也不能补规则答案变成通过。

原始证据：`backend/data/acceptance/model-suitability-live.json`；复现入口：`python -m scripts.compare_agent_models`。这是6个代表场景的小样本，不能推断所有推荐、售后和长会话都已验证。

## 3. 逐个默认选择

### 业务Agent：DeepSeek Flash

业务Agent需要稳定执行目录了解、需求拆解、参数提取、预算/数量过滤、多轮上下文和权限工具。GLM在当前关键推荐场景中不够稳定，因此不全量切换。按用户允许的“不够用再用DeepSeek”，保留DeepSeek Flash；不使用Pro。

### 评测Agent：GLM-4-Flash规划，实际业务模型作为被测对象

规划只在白名单能力内调用read_test_capabilities与propose_test_plan，计划必须审核；真实规划已在接口及浏览器验收中通过。此受限任务当前够用，默认GLM-4-Flash。

被测助手仍是真实业务Agent，默认DeepSeek Flash；工具参数、回答事实、归属和预算由硬断言判定。没有宣称GLM已胜任未经标定的开放式语义裁判，也不让其一句“通过”覆盖失败断言。

### 功能测试Agent：GLM-4-Flash规划，固定业务断言执行

同样使用GLM真实规划，从审核用例中选任务；随后执行真实API、状态或浏览器验证。新增功能用例也走固定动作与JSON断言，不能执行模型生成的任意命令/SQL/URL。GLM规划多用例报告与自建功能用例均真实通过，因此本职责默认GLM够用。

功能执行阶段模型调用数为0是正常的，规划阶段仍有真实GLM调用与usage；界面分别展示两者，不把它混称“全部没调模型”。

## 4. 默认配置与报告

- CLOUD_MODEL=deepseek-flash：业务助手。
- QA_CHAT_MODEL=glm-4-flash：两个测试Agent的规划。
- QA_TARGET_CHAT_MODEL留空：被测对象继承实际业务模型；模型对照实验可显式覆盖，但不改变服务默认值。
- 测试模型没有隐藏付费回退；失败保留阻塞，模型配置变化使正式计划需要重新审批。独立Embedding配置不受影响。
- 正式计划必须model规划；助手必须live；服务端校验真实规划工具与HTTP计量。平台确定性诊断需显式diagnostic=true，不能算正式Agent模型验收。历史规则记录保留并明确标注。

## 6. 本地生效步骤

在原启动终端正常停止旧API和worker后，在backend目录分别运行：

```powershell
.venv/Scripts/python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000
.venv/Scripts/python.exe -m app.quality.worker
```

两条命令在独立终端运行；不要在旧进程未停止时重复启动worker。完成后刷新OP；真实店铺、账号及订单不需要重新初始化。
