# 总览与两类自建用例增量需求 / 技术方案

## 需求

- 总览业务卡展示对话/工具与入口，不把业务助手包装为测试执行器。两类测试卡展示各自用例与运行，区分已登记与真实通过。
- OP正式Agent评测必须使用真实模型：助手为live，功能由真实模型规划后使用固定业务断言。服务端约束与界面一致；显式diagnostic=true只用于平台自身确定性诊断，不算Agent效果验收，历史报告仍可查看。
- 两类测试均可人工新建、编辑候选、审核、追加新版本、撤销、纳入计划。已有助手用例支持问题/工具/文字断言；新增功能用例支持固定动作与响应硬断言。
- 测试模型读取服务器QA_CHAT配置，本地glm-4-flash独立密钥；不把配置或密钥传给浏览器。失败阻塞，不能偷偷切付费模型或规则结果。

## 技术方案

复用QualityCaseVersion JSON specification，不增加草稿表。kind=assistant/functional决定schema及固定adapter；既有助手版本不带kind时按assistant解析。版本不可跨类型修改。

功能schema只开放白名单动作：商品列表、商品详情、读取购物车、加购、本人订单。每步选择合成买家/商家/匿名角色、业务ID/数量、预期HTTP状态及可选JSON字段断言。JSON路径只允许有限层字典键/数组下标；不支持表达式、URL、脚本、SQL、变量插值或凭据。

子进程登录合成身份，固定nanzhi测试店铺，通过真实业务API执行每步；每步核对HTTP及声明的字段值/包含关系/长度。清理、共享预算、审批快照和版本撤销沿用现有父任务机制。模型只负责选择已授权用例，不能改写硬断言或生成任意执行代码。

OP默认仅显示正式真实模式入口；确定性诊断仍供明确的平台自测API使用。CI无密钥诊断与实际glm模型验收分别出具记录，不混算通过率。

## 验收

两类自建用例审批、不可变版本、类型权限、跨类型拒绝与反注入专项通过；功能固定动作实际写合成购物车并读取核对。再通过真实GLM规划执行新增功能用例，保留模型usage与逐步HTTP断言。规则诊断无法被误标为正式模型验收。
