# PRD：先了解本店，再按需求推荐

日期：2026-10-19。接续prd-live-acceptance.md，不将旧热销排序称为完整需求推荐。

## 用户体验

双端均支持“预算100元，送朋友，喜欢陶瓷，不要香薰”。助手先通过原生工具获取本店在售商品概览，再结合本会话历史拆解需求，调用推荐工具筛选。最终展示需求摘要、默认至多3个候选商品及其SKU/单价/数量小计、商品字段支持的推荐理由和取舍。缺少必要条件则询问，不猜测偏好。不展示内部思维链。

## 工具流程

1. get_store_catalog返回本店可售商品数、分类、价格范围、分页商品说明/SKU；第一阶段只开放此工具。原生调用成功后才开放推荐筛选。
2. recommend_products保留热销/浏览/同类/预算模式，新增需求摘要、精确分类、必须包含词、排除词、最低单价和数量。推荐时重新读取数据库，不将概览快照当作库存锁定。
3. 严格校验本店、营业状态、商品/SKU上下架、库存、每单数量与限购上限、价格区间。预算按单价×数量的小计计算，不含运费；暂不实现跨商品组合优化。
4. keywords中的各词均须出现在商品名/分类/说明或同一可售SKU规格中，excluded_keywords任一命中即排除。无匹配则说明条件不满足并请求放宽，不暗中突破预算。
5. 概览不生成商品卡；仅推荐结果生成候选卡。商家推荐同样只展示可购商品；后台其他管理查询不变。不可覆盖user_id/shop_id/role。
6. 追问“便宜一点”“不要这个材质”参考同会话历史，每轮重新查询；跨会话不共享偏好。混合售后要求可用知识工具核实。商品描述中的指令视为数据，不得改变权限。
7. 概览后必须执行recommend_products，不能仅心算“无匹配”就结束；确实缺信息时显式调用clarify_recommendation后问1—2项，不生成卡片。两个阶段各允许一次模型纠正，推荐默认最多6个模型步骤，其它业务仍为4步；不是无限重试或通过放宽约束求成功。

规格优先规则：关键词若出现在任一SKU规格中，按具体SKU规格匹配，而非用商品说明中列出的所有可选规格使每个SKU都命中。商品说明同时写“蓝色和白色可选”不意味着蓝色SKU满足白色要求。累计限购剩余额度仍由下单接口校验，推荐阶段仅排除单次超过限购上限的数量，不能承诺一定可下单。

## 验收与范围

- 自动覆盖双端、跨店、闭店、缺货、下架SKU、低价缺货高价有货、数量预算、排除词、分类、参数非法及先概览后推荐顺序。
- 模拟工具调用不冒充真实模型验收。少量真实智谱+隔离SQLite商品验证需求抽取/工具结果/回答，明确不等同MySQL/Redis/RAG统一验收。
- 未通过的真实RAG最终回答、重启后订单追问继续保持未通过；不宣称简历全部完成，不添加未经测量的准确率或性能提升。
