# 测试模块详解

## 一、测试分层，以及每层能证明什么

测试分四层：常规接口与单元测试、前端行为测试、Agent 评测、真实环境验收。关键认知是**每一层只能证明它那一层的事**——接口测试通过不等于 Agent 表现好，Agent 评测通过不等于真实依赖没问题，合成数据档通过不等于真实店铺通过。所以产品文案里明确写了"接入数量与运行通过数量分开""缺依赖记阻塞"这类限定，不用一个绿色状态掩盖没接入的部分。

还有一条区分必须反复强调：**代码已写、用例已登记、真实验收通过，这三件事不是一回事，必须分别统计。** 很多汇报的失真就出在把"代码写完了"说成"验证通过了"。

## 二、常规测试的工程化

整套测试的隔离地基是**在导入任何应用模块之前，用环境变量把外部依赖降级为确定性桩**：数据库换成内存库、缓存换成进程内存、模型走规则模式、关掉真实向量检索与严格依赖，同时清空云端向量配置以防测试意外打真实云服务。在此之上，每个用例都会重建全部表结构并清空缓存，所以用例之间互不干扰。真实依赖档有一个开关：一旦提供了真实数据库地址，就不再覆盖数据库与缓存配置——**一套测试代码，两种档位。**

有一个刻意的选择值得讲：**整套测试没有使用框架提供的依赖覆盖机制**，所有伪造都在三个层面完成——进程级环境变量、针对传输层或配置属性的打桩、以及整根替换测试客户端的请求方法。为什么这样？因为依赖覆盖只伪造了应用内部的一条路径，而环境变量是"整个进程都以为自己跑在内存库上"，更接近真实部署形态，也更难被某条绕过路径逃掉。

还有一个夹具设计体现了安全立场：跨店测试需要商家身份，夹具**直接操作数据库写入显式授权记录**，而不是让测试走公开注册接口自授商家身份，文件注释明确写着这是"跨店测试用的显式授权，绝不用公开注册"。**测试不能为了省事而使用生产里被禁止的路径**，否则这条禁令就没有测试覆盖了。

## 三、用例锁定了哪些不变量

常规用例集中在六类不变量上。**隔离类**：别的商家读不到本店订单；客服会话按用户、店铺、订单三重隔离；自定义用例的工具审计必须"本轮加本用户加本会话"才算数（用六种参数逐一证明只有正确的那种能通过）。**库存类**：库存不足不可超卖；下单精确扣减指定规格且其它规格不动。**权限类**：401 与 403 两层分开测；令牌里的角色不可信（把角色改成商家仍然被拒）；公开注册不能自授商家。

**幂等类**：提案确认幂等、并发确认只创建一个商品；重复领券不消耗名额；平台取消订单库存只回补一次。**并发类**：限购在预留库存前跨全部规格累计（被拒后两个规格库存都不变）；订单号在提交前就唯一；用两个独立会话携带过期快照回补库存，最终结果是正确累加而不是互相覆盖。**缓存类**：新增评价后缓存里的评分立即更新；先预热商品缓存再冻结店铺，断言买家侧商品为空——**这说明测的是"缓存不会绕过状态检查"，而不是"缓存被清掉了"。**

**这些用例不是"永远绿的装饰"。** 有真实的先红后绿记录：某一批曾出现三个失败（隔离工作进程的预算保留、助手用例适配器与模式的完整性、报告日期的时区切分），后来全部修绿；另一批出现一个失败（普通网页请求应保持在业务网页根目录），也在补齐配置后转绿。**"测试真的抓到过问题"是测试有效的最强证据**，比"全绿"更有说服力。

## 四、前端行为测试的做法

这个机制需要说准，因为它很容易被面试官抓细节：**它不是用浏览器模拟库，也不是无头浏览器**。做法是读取被测源码、按标记切出目标函数片段、在隔离的执行上下文里注入**手写的文档对象桩**（自己实现的元素类、存储映射表、创建元素的方法），然后跑断言。整个仓库**没有前端包管理配置**，唯一的浏览器自动化脚本单独一个、需要私有凭据与目标地址两个环境变量；**持续集成里只跑其中一个脚本**，其余十几个是本地开发期的快速回归。这一点必须主动说清，否则被问"这些脚本谁在跑"就会露怯。

这些脚本锁定的内容很实在：安全渲染（渲染带标签和事件的恶意内容后，断言**没有产生任何图片或脚本节点**、原文以纯文本保留）；令牌共享与登出的边界（同源新标签页共享账号会话、登出只清当前端的令牌、共享账号下登出同时吊销两端、认证失败清凭证但无权限不清）；迟到响应不落地（在途请求遇到账号切换必须中止且不覆盖已有数据）；草稿与版本冲突；以及一个很特别的**跨语言契约**——用后端读取默认配置值，断言前端默认值与后端的完全一致。源码级断言也放在这里：断言买家和商家页面**不包含**测试中心的任何脚本引用，只有运营页面包含——**"测试资源不泄露给业务端"这个边界同时被后端权限和前端源码两侧锁住。**

## 五、测试平台：用例体系与规划批准

要先分清项目里有三个 Agent：**业务助手是被测对象**，评测 Agent 负责给业务助手出题、执行、判分，功能测试 Agent 负责跑已登记的接口用例与真实浏览器用例；两个测试 Agent 不互相聊天，只共用一套受限执行框架，"联合运行"只是调度方式。另一个关键区分是：**评测 Agent 的规划模型不等于被测业务助手的业务模型**，配置一变已批准的计划会自动作废。

**用例体系是声明式的。** 每个助手用例由若干轮对话组成，每轮声明"用户说什么、必须调用哪些能力、回答必须包含什么、不得包含什么"。三条硬约束：必须调用的能力只能引用已登记的能力；**每轮至少要有一个硬断言**（直接禁掉"建个没断言的用例让它自动通过"这条捷径）；轮数与字数都有上限。功能用例结构类似：固定业务动作加受限参数加结构化断言，动作与期望状态码都是白名单。**整套执行器最后有一句兜底——不认识的用例一律抛错**，这是白名单而非黑名单的写法。用例还有完整的版本生命周期：新建必然是"候选"状态且不可执行；已审核的版本**不可修改**，要改必须创建新版本；撤销后执行时会被拒绝——目的都是"已批准的东西不能被悄悄改"。

**规划时只给模型两个能力**：读取"我有权限的用例清单"、提交一份待批准的计划。没有文件系统、没有命令执行、没有数据库；并且用状态约束顺序（必须先读过清单才能提计划，**防止它凭记忆编造用例编号**）、严格限制选择范围（只能从本次授权的候选集合里挑，这个子集校验在三个层次各做一次）。**计划必须人工批准才能执行**，批准要把计划内容摘要、被测代码指纹、用例集合版本、模型配置四样一起绑定。

## 六、测试平台：隔离执行、预算与报告

**执行是真的隔离。** 每条用例在一个独立子进程里跑，有独立临时目录；子进程带一个不可伪造的隔离标记作为通行证，没有它就拒绝加载测试配置——因此服务进程本身**无法**在请求线程里跑测试，也**无法**误用测试模型。子进程禁用第三方测试插件自动加载（保证结果可复现），结果文件有大小上限，单条用例有硬超时，并且**按平台差异杀整棵进程树**（因为测试框架与浏览器会拉起子进程，只杀父进程会留僵尸）。数据隔离分两档：合成档用内存数据库加内存缓存；真实依赖档用**独立命名的一次性数据库与独立缓存命名空间**，并对驱动类型、主机、端口、库名格式做多重校验，**物理上不可能和业务库同名**。

**预算计量在出网请求层拦截并计数**，同时覆盖聊天与向量两类调用并分开记账。三个做法值得讲：**预算在发送前检查**（不能"先发了才发现超预算"，测试还会断言"真的没发出去"）；**保守预留加真实用量修正**；**中断时按剩余额度保守占用**（子进程被杀时可能已花钱但拿不到用量，宁高不低）。预算耗尽的用例记"阻塞"而不是"失败"——**"预算不够"不是"被测系统有问题"**。一份计划的预算是所有用例共享的，跑了几条后额度耗尽会被明确记为"父任务共享预算已耗尽"。

**报告固定三栏**：用例与步骤、请求与对话与工具与检索证据、可信事实与断言。证据是**自动采集**的——在测试客户端层拦截所有请求，自动记录方法、路径、入参、状态、出参、耗时；用拦截而不是让每个用例手写，好处是证据完整且不可能忘，也不受用例作者主观影响。**自动采集是证据可信的前提**，手写的证据你无法判断它是否选择性记录。截图这类产物有四道校验：文件名格式白名单、路径必须在根目录内、**内容哈希必须等于运行时记录的哈希**（防截图被替换）、必须被该次运行的证据声明过（用另一次运行的编号取同一张图应当失败）。报告对比也有方法论：只有环境、数据版本、执行模式都相同、双方都已结束、且用例版本摘要相同时才判定退步或改进，否则一律标为不可比并明示原因；新增和删除的用例单列，不进任何涨跌统计。保留策略只自动清理已结束且超期（默认七天）的运行及其不再被引用的截图，**计划与活动任务永不自动删除**；手动清理要先预览后确认，确认时必须带上预览时算出的范围摘要。

## 七、判定门禁：不许假装通过

这是整个测试体系最核心的机制。一条用例拿到"通过"之后，还要**逐条复核证据**，任何一条不满足就降级为"阻塞"：**必须有断言、且全部通过、且清理确认**（堵住"什么都没断言就返回通过"和"测试数据没清干净"）；**正式的助手评测必须有真实模型调用计量，且每次对话的执行模式必须是真实模型**（堵住"用规则兜底冒充真实模型通过"）；**真实依赖档必须有真实数据库与缓存的执行证明**（堵住"声称跑了真实数据库，实际跑到内存库上去了"）；**功能用例必须真的被收集并执行过，且不允许任何跳过或失败**。

第四条特别值得展开，它是一个很好的洞察：常规测试框架里最阴的"假通过"不是断言写错，而是用例被**静默跳过**、或者测试函数体是空的（收集到了但根本没进入执行阶段）、或者在准备阶段就出错。所以断言必须是"**必须存在一个真正执行并通过的阶段，且不允许任何非通过**"，而**不是"框架退出码是零"——退出码零在全部被跳过的情况下也是零。** 另外还有"清理失败不放行"，以及一条容易忽略的口径：**不把不同类型的用例合并成一个总通过率**——合并会让"助手全挂但接口全过"看起来像"通过率五成，还行"。

## 八、版本绑定：旧结论不能证明新代码

一个"全部通过"的报告，如果三天后有人改了代码或换了模型，那个报告就失效了。所以必须把结论绑到"它当时测的是什么"：**计划内容摘要、被测代码指纹、用例集合版本、模型配置**四样，再加上**批准人的权限**（批准人自己被撤权，计划也应失效）。而且**执行前必须重新校验一遍，不能只信批准时那一次**——计划可能在排队期间被打扰。这条原则对任何"先批准后执行"的系统都适用。

计算代码指纹时有一个很聪明的细节：**排除"给人看的用例说明文档"**。这些文件只放步骤与预期，不参与执行；如果算进指纹，那么"给用例补一句说明"就会让所有已批准的计划失效——**那就没人愿意补文档了。** 这是一个把"给人看的"和"机器执行的"解耦的取舍，体现的是考虑过人的行为，不只是技术正确性。

## 九、持续集成的分工与覆盖范围

主流水线在推送到主分支时跑全量后端测试与前端语法检查，然后部署。质量流水线由路径触发——只有改动落在测试平台相关文件上才跑，因为它要安装浏览器运行时、要跑真实浏览器用例，成本高。它跑的内容包括：唯一那个浏览器自动化脚本、一批平台自身的测试、两组固定用例的真隔离执行，并把证据作为构建产物上传，保留期七天，与报告保留策略一致。**这个路径过滤是一个务实的成本取舍**：不是每次提交都跑最贵的测试，但改到这些文件时一定跑。同时要主动说明——**那十几个前端脚本不在持续集成里**，这是当前的覆盖缺口。

## 十、真实环境验收的纪律，以及数字口径

分三档：合成档（确定性强、便宜、可重复）、真实依赖档（一次性数据库加独立缓存命名空间，验真实数据库与缓存行为）、真实店铺档（线上站点、真实模型、真实浏览器）。档位切换是**整体替换**而不是"多加几条用例"，因为两档的数据准备、用例定义、断言方式完全不同；混在一起就会出现"用合成档的绿灯声称实店通过"。实店档的纪律和合成档完全不同：只接受登记过的受控用例；被测助手必须是真实模型模式；目标站点是硬编码白名单（换域名在创建任何身份之前就拒绝）；要校验"远端确实就是本地这个库"；清理只按**不可猜测的批次标记**匹配。然后是要主动划清的边界：演示支付与物流**不是真实支付和快递**，售后解决**不涉及真实资金退款**——**主动承认这些边界，比被追问出来强得多。**

几个容易讲错、必须说准的数字口径：当前工作区的测试函数约三百五十个，因为存在参数化，实际**收集到的用例约四百二十个**；测试平台目录里有**九十一**条活跃用例；"三百八十五项通过"是**发布快照上的历史记录，不是当前工作区**；测试平台的十条"平台自身工程测试"需求**只是需求定义，没有登记进一键运行**。已知短板：前端脚本大部分不在持续集成里；平台用例的清理上限只有一个自由文本提示，没有机器可读的截断标记；内存缓存档不支持跨进程互斥；语义评分未实现（硬断言是唯一判定依据）；真实负载基准未做；部分用例执行时会直接改全局配置，**并行执行会互相污染**。最后是一条贯穿全篇的纪律：**同一批用例的通过报告与阻塞报告都要保留、分开引用，不能只挑通过的那份说。**
