# 三个 Agent 能力审查

此文保留审查时的问题与复现口径。后续修复和首次使用说明见 `three-agents-assurance-20261023.md`，不将历史审查当作当前未修状态。

审查日期：2026-10-21（北京时间）。代码基线：270a8ea；审查期间未修改业务实现、密钥或店铺数据。

## 1. 结论

三个 Agent 已经有真实执行链路，不只是展示页面。但它们的成熟度不同：业务 Agent 是受控业务助手；功能测试 Agent 是基于已登记能力的规划和复合测试工具编排；评测 Agent 是程序核验、独立模型评分与人工复核的组合。

不能据此宣称：自由探索全站、任意需求自动生成可靠测试、全部功能覆盖、全部模型质量验收完成，或具备完整的安全评测能力。本轮没有发现足以确认的跨店数据泄漏，但审查和现有测试也不是“没有安全问题”的证明。

本轮发现 6 项需修正的问题，以及配置和产品表达差异。风险主要在评测结论可信度、功能接入覆盖、模型执行身份及撤权控制。

## 2. 验证范围与口径

- 阅读业务编排、角色工具、商品与店铺检索、计划、审批、子进程执行、评测、隐藏集、功能目录和 OP 页面实现。
- 运行 9 个相关测试文件：66 passed。覆盖评测、执行边界、版本审批、隐藏集/稳定性、自由需求受理、自定义用例、B/C 商品权限和检索。
- Python Playwright 隔离浏览器验收 37 项通过；6 个 OP 非浏览器 Node 回归通过。另两个 Node 浏览器脚本因缺少 Node playwright 包未运行，不能记通过；本轮浏览器依据来自上述 Python 验收，不是对两个脚本的等价覆盖声明。
- 新增 `backend/scripts/audit_three_agents.py`：5 组纯合成探针均复现问题。探针成功意味着“问题被复现”，不是产品能力通过。
- 读取当前本地模型名称和执行开关，不读取或展示密钥内容。
- 本轮未调用云模型、未执行实店写入、未重新做生产 UI 全量验收。既有真实模型报告只作为历史证据，不等同当前版本全场景重验。
- 测试首次因引用了不存在的测试文件而未运行；更正文件列表后 66 项正常通过。

复现命令（在 backend 中）：`.venv/Scripts/python.exe -m scripts.audit_three_agents`。

## 3. 业务 Agent

### 已实现

- C 端购物小助手和 B 端运营小助手：身份由服务端上下文绑定，工具参数不能任意覆盖店铺或用户。
- 当前 13 个业务工具，C 端不可用的 4 个为：经营概览、低库存、商品草稿提案、后台操作指导。
- 商品搜索包含 SPU 名称、分类、描述、标签与 SKU 规格、参数；有局部同义词和语义兜底。
- 商品图片有独立向量检索与 SPU/SKU 关联；不是把图片地址当作图片语义。
- 店铺设置、优惠券、评论、购物车、订单、物流、售后及 B 端固定操作说明可查询。私有数据先按身份限制，再检索，最终重新读取 SQL 事实。
- 多轮会话、摘要、历史恢复、商品推荐卡、工具轨迹、失败处理及回答来源隐藏。
- 严格模式下模型/工具失败返回失败，不用规则答案冒充成功。

### 边界

- 不应把所有库存、价格和订单事实固定进向量后直接作为答案：现有“向量定位，SQL 复核”方向正确。
- B 端操作指导不是自动执行配置。商品提案不是模型直接上架；购买等动作仍需用户确认和业务接口校验。
- OP 业务工作台使用合成副本，不能把其中的目录当作真实南枝店全部商品。
- 会话摘要和受限查询不是完整长期用户画像，也不是持续自主学习。
- 某些快捷操作说明走 direct 回复；严格模型模式不意味着每个用户输入都会消耗 LLM。真实模型测试必须核对实际 mode 与模型 HTTP 证据，不能只看开关名称。

### 问题 B-01｜P2：字面命中会阻断语义补充召回

位置：`backend/app/services/product_search.py:63`、`backend/app/services/product_search.py:81`。

存在任何字面命中就直接返回，不再做语义召回合并。探针中一个商品精确匹配“马克杯”，另一个没有相同名称但可由语义通道召回；最终只返回第一个，语义通道调用次数为 0。这是确定的检索策略限制，不是一次真实模型召回率测量。

继续追踪底层后确认 `backend/app/rag/knowledge.py:100` 实际有 `rag_max_distance` 过滤，因此不应指称“没有相关性门槛”。当前是否需要调整阈值，应另用标注查询集校准，不能仅凭调用层没写过滤就认定底层未过滤。

建议：以标注查询集校准不同 Embedding 模型的相关性门槛，合并字面与语义候选并重排，保留“没有匹配商品”的能力。不要随意照搬某个 distance 常数。

验收：食品无货、被芯同义词、SKU 参数、描述命中、模糊用途、多商品混合命中分别测精确率与召回；库存和权限仍在 SQL 层二次校验。

## 4. 功能测试 Agent

### 已实现

- 自由需求受理：真实模型读取当前功能目录，给出可实现性、对应用例和缺覆盖说明。
- 模型规划、计划版本绑定、人工批准、队列、隔离子进程、超时、模型预算和证据报告。
- 模型先调用 `read_bc_features`，再调用批准的 `execute_registered_case`；业务断言由固定 API/UI 测试执行，不由模型自报通过。
- 可添加声明式功能用例，审核后执行；不接受任意 URL、SQL、shell 或模型生成脚本。
- 自定义功能步骤目前只允许 catalog、product、cart、add_cart、orders 五类动作。新增任意优惠券、装修或上传测试流程，仍需先接入受限执行适配，不能只写自然语言就任意运行。
- 有实际浏览器、固定接口回归和可复用页面动作；不是仅检查网页截图。
- 有正常版/缺陷注入版对照，当前注入范围为运费、订单金额、库存校验、买家访问商家权限 4 个场景。

### 实际覆盖

当前本地目录共 104 个 active 登记项：40 个业务助手场景，64 个功能场景。功能场景由 43 个 pytest 适配、8 个浏览器适配、13 个 UI 动作适配组成。登记数不是通过数。

功能目录有 17 个域、99 个接口入口；UI 动作定义中 12 个 ready、2 个 unverified。接口发现不等于每个分支已测试。

### 问题 F-01｜P2：正式计划可显式关闭功能模型执行环节

位置：`backend/app/quality/service.py:75`、`backend/app/quality/worker.py:38`。

`functional_driver` 仅在调用方没传时才默认开启。探针提交 `kind=functional, diagnostic=false, planner=model, functional_driver=false` 被接受。规划可仍调用真实模型，但执行会跳过功能 Agent 的工具调用环节，走固定执行器。

这不代表完全没有模型调用，也不是权限越权；问题是“真实功能 Agent 执行”与“模型规划后固定回归”的产品口径可混淆。

建议：正式功能 Agent 计划强制启用 driver；固定回归保留为显式诊断模式，并分别统计两种链路。

### 问题 F-02｜P2：19 个 active 功能场景未接入模型功能目录

位置：`backend/app/quality/feature_catalog.py` 的 bind_plan、`backend/app/quality/functional_driver.py:22`。

本轮计算未关联的场景为 F31—F43 和 E03—E08，共 19 个。它们有固定执行适配，不是没有测试代码；但不在模型可调用的 `(case_id, feature_id)` 目录映射中。正式 driver 计划会遇到 unmapped 阻塞或无法执行。

当前“业务助手与会话、地址、浏览历史、上传”四个功能域无可调用测试工具。不要把 99 个发现接口包装成全覆盖。

建议：逐项补充映射或准确标记“仅诊断可运行”，添加“所有声明支持模型执行的 active 用例均具备合法映射”的回归门禁。

### 实店与隔离环境差异

当前本地只启用 isolated-local/native-local。实店 profile 有独立受控适配，但计划会强制 diagnostic=true、fixed 规划；自由需求受理在实店也会关闭 driver。因此实店 API/UI 自动化不应称为“功能测试 Agent 真实自主编排”。这是有意限制，不宜通过取消隔离保护来修正。

## 5. 评测 Agent

### 已实现

- 测试对象包括业务 Agent 和功能测试 Agent，不只是业务接口。
- 来源运行冻结为证据快照；支持多用例汇总报告，不要求每条用例各建一份报告。
- 程序核验、独立模型分维度评分、人工意见分别保存；模型输出必须符合 schema，并引用已存在的证据 ID。
- 支持版本对比、同计划重复运行稳定性、隐藏评测文件和需权限揭示、已知缺陷检出校准。
- 证据过长时明确拒绝，不静默截断完整会话；模型评分实际走受限子进程。

### 问题 E-01｜P2：业务来源为 blocked，程序核验仍可 passed

位置：`backend/app/quality/agent_evaluation.py:65`。

程序只核对断言、清理、问答、工具轨迹和范围，没有把业务来源状态纳入判断。探针构造 blocked 来源、已通过的前置断言、正常问答与工具记录，得到 program.decision=passed。

这说明状态矛盾没有被防御，不证明线上已有此类错报。功能测试 Agent 报告产品 failed 可以是有效测试行为，修正时不能反过来一律扣测试 Agent 分。

建议：按对象分别检查来源状态和证据一致性；业务 blocked/cancelled 不能被任务成功程序核验覆盖。验收包含“部分准备成功后环境阻塞”“报告状态与断言矛盾”。

### 问题 E-02｜P2：隐藏集只检查测试执行标记，且部分答案可令整集 passed

位置：`backend/app/quality/heldout.py:24`、`backend/app/quality/heldout.py:104`。

三个条目都读取同一个通用断言“固定回归确实收集并执行且未跳过”的 passed，而不是非法数量、库存或权限的实际业务值。

探针只提供一条隐藏答案，构造 F11 整体 failed、业务断言 failed、通用执行标记 true，结果隐藏集 passed=true；其余两条仍为 expectation_unavailable。当前通过只表示可评分子集的通用标记匹配，不能证明隐藏业务集通过。

建议：每个条目绑定真正的业务观察值；输出 expected/scored/missing 数量，任一必需条目缺失则整集 incomplete。生产缺答案文件时应继续明确未启用，不自动填答案绕过。

### 问题 E-03｜P2：缺陷基准链路不响应中途撤权

位置：`backend/app/api/agent_quality.py:193`、`backend/app/quality/agent_evaluation.py:203`。

API 入口校验执行授权，但校准函数向每个执行器传入 `lambda:False`。探针记录 4 场景×正常/缺陷 8 次执行的取消回调，全部固定 false；没有像普通计划或模型评分那样重新检查执行者授权。每个子步骤仍有时间/模型预算，不代表完全无限制。

建议：从 API 传递真实撤权回调，步骤间也检查；增加整体预算、并发和限频保护，避免 8 个子预算被误解成一个总预算。验收在第一个子场景后撤销 qa.functional.run，后续子场景必须停止。

### 评分能力边界

- 模型评分是辅助判断，不是事实真值。schema 验证只能证明引用 ID 存在，不能证明理由与该证据相符。
- 7 个业务维度与 8 个功能维度已定义，但没有观察到的权限恢复场景不能拿流畅文字替代。
- 4 个注入场景的检出率不能解释为全站缺陷检出率。
- 本轮没有新跑付费模型对照，因此不对当前模型准确率、P95 时延或成本给出未经测量的数据。

## 6. 模型、文档与运维差异

- 本地实际业务模型为 deepseek-flash，测试/评测模型也为 deepseek-flash；并非早期要求的 GLM-4-Flash。被测模型覆盖配置为空，意味着继承业务模型。是否改回 GLM 应重新测工具契约与评分质量，不能仅改展示文案。
- 评测与被测对象是独立调用和独立职责，但当前相同模型名称不等于异构模型裁判。仍需人类标注对照集验证偏差和评测稳定性。
- 文本 Embedding 为 qwen3.7-text-embedding。图片 Embedding 是独立链路，不能从文本模型配置推断图片索引状态。
- 业务运行要求真实模型，严格失败不回退；质量端确实保留显式诊断规则模式。UI 必须区分这两种口径。
- 技术文档仍有 74/91 条、导航顺序、GLM 默认值、尚未交付条目等历史基线；应标注历史版本并增加“当前能力快照”，避免把旧文档当现状。
- 来源隐藏只应作用于对话回答，OP 内部脱敏轨迹与审计证据仍需保留。不能为了页面干净删除可追责数据。

### 按 Agent 构成理解当前实现

- 大脑：配置化云模型；测试子进程使用独立配置入口。更换模型会涉及工具契约与审批指纹，不是纯 UI 设置。
- 感知：用户文字、鉴权身份、业务工具结果和运行证据；图片索引检索不等于已经支持任意上传图像的多模态会话。
- 规划：业务模型选工具；功能模型受目录和批准场景约束；评测模型按固定量表读取证据。
- 短期记忆：业务会话历史与摘要；测试运行保存计划和当前工具会话。
- 长期记忆：店铺知识/图片索引与历史报告，不是自动学习用户偏好或自我改写技能。
- 工具与行动：结构化白名单、参数校验和固定执行器；没有向模型开放任意终端。
- 知识与指令：角色提示、店铺资料、B 端手册、功能目录和评分规则。尚不能据此称“完整外部 MCP/Skills 平台”。
- 编排：有 API、队列、worker、租约、子进程、审批、快照与报告；不是三个模型自由互聊协作。
- 护栏：有身份、店铺、工具、审批、预算、证据脱敏；E-03 说明部分辅助链路仍未贯通撤权。可视化展示的是可审计动作和结果，不应暴露模型私有思维过程。

## 7. 修正顺序与完成标准

1. 先修 E-01/E-02：阻塞与缺失证据不算通过，隐藏集改真业务观察值，补反例测试。
2. 修 F-01/F-02：固定回归和 Agent 执行分开统计，逐项补齐 19 个场景目录映射或收窄支持声明。
3. 修 E-03：撤权、取消、整体预算贯通缺陷基准。
4. 修 B-01：建立相关性数据集和混合召回方案，分别测不同 Embedding 模型，不盲设阈值。
5. 同步 PRD、模型配置说明、OP 能力展示和环境标记；再做真实模型代表场景验收，逐条保留运行 ID/模型名/调用量/断言。

本轮交付的是审查，不是上述修复已完成。66 项既有回归通过与 5 组问题探针同时成立：原测试没有覆盖这些反例。
