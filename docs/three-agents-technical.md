# 三个 Agent：技术方案与实施顺序

依赖需求：prd-three-agents.md。状态：设计基线，尚非全量实现记录。

## 1. 复用架构

业务层复用 backend/app/agent 的 assistant、tools、guard、context、summarizer 及现有 RAG 服务；FastAPI 接收身份，SQLAlchemy 是访问 MySQL 的 ORM，Redis 是缓存/会话/队列，三者职责不同，不相互替代。Chroma 负责语义向量索引，不作为订单事实库。

测试平台复用 app/quality 的 catalog、planner、service、queue、worker、sandbox、scenarios 和 case_runner。两个测试 Agent 使用不同规划提示、执行白名单及数据副本；联合运行是调度方式，不增加第四个 Agent。

## 2. 控制流与状态

OP 请求→OP及质量权限→计划 schema 校验→固定计划或受限模型规划→版本/目录/代码指纹摘要→人工批准→MySQL任务记录+Redis排队→worker租约→隔离执行→脱敏证据→断言判定→分组报告。

计划沿用 planning/planning_running/draft/approved/blocked；运行沿用 queued/running/completed/failed/blocked/cancelled。进程崩溃、租约过期不自动重放未知写操作。取消与撤权要在步骤边界和运行轮询检查。重跑创建新 run，不覆盖旧证据。

## 3. 用例与证据契约

每条用例记录 ID、版本、需求关联、目标角色、模式、环境、准备数据、步骤、允许工具、断言、清理。catalog 只有存在可执行适配和回归验证才置 active；candidate 不能执行。

执行返回 status、requests、tool trace、facts、assertions、budget、cleanup；新增 RAG 证据包括文档版本、chunk ID、检索分数、来源及引用对应关系。不得用“模型说成功”代替业务数据库断言。

用例台账与执行历史分离。后续版本编辑采用追加修订，旧报告引用旧版，审批绑定快照。比较仅限相同目标/模式/环境/数据版本；不同环境不能直接合并通过率。

## 4. 环境适配

快速档保留每用例子进程 SQLite/MemoryRedis，适合确定性回归。真实依赖档新增服务端固定 profile，不接受用户 URL/SQL/命令：数据库名称必须专用 qa 前缀、拒绝与业务 DB 同名；Redis 使用专用实例或经验证命名空间；Chroma 使用工作区独立目录。无明确隔离证明则阻塞。

真实档准备合成多店、多用户、多SKU、优惠券、订单和政策数据，执行后核查与清理。MySQL 不支持仅靠一次外层事务撤销全部跨请求提交，因此采用独立数据库生命周期，不对实际业务库做 TRUNCATE。

真实 RAG 先导入固定政策→真实 Embedding→Chroma计数及版本核对→语义查询→业务助手回答→引用和事实断言；无命中、更新、冲突分别测试。计量覆盖 Embedding 与聊天，模型失败明确阻塞。

## 5. 业务助手补强策略

先读取目录摘要，再将用户条件结构化；通过业务查询过滤下架/禁售/无库存项，组合推荐在代码中校验数量乘SKU价格之和。上下文保存商品/SKU/订单实体及预算约束，过长历史摘要保留关键事实，身份不能进入可被模型覆盖的参数。

快速事实查询只走确定性业务工具，复杂推荐走真实 Function Calling。缓存只存按店铺和目录版本划分的可公开摘要；订单结果不共享缓存，价格库存落单前重新校验。先测量耗时再优化，不通过取消权限检查提速。

## 6. OP 页面与接口

侧栏独立 Agent 与测试中心；第一步把已有四个测试入口移出管理与审计，后续加入三个 Agent 总览与业务能力页。复用 op-quality.js/css，不引入新前端框架，不在B/C加载测试模块。

现有 /op/qa 的 capabilities/cases/plans/runs/report 接口继续复用。新增能力/版本、用例修订、对比及保留策略接口时沿用 require_operator+质量grant，不以隐藏按钮替代服务端授权。

## 7. 实施批次与验收

1. 分区、总需求与技术基线：导航回归、B/C无测试资源泄漏。
2. F剩余10项：优先复用已有真实业务专项测试；每项证明固定节点执行，禁止空测试通过。
3. A剩余29项：按推荐、多轮、订单、安全、提案、知识分组补执行器；暴露业务缺陷先修业务，再跑断言，不放宽标准。
4. 原生依赖与RAG：专用库/命名空间预检、真实模型和Embedding计量、故障/清理验收。
5. OP能力可视化、版本化用例、报告对比与清理；浏览器E2E独立证据，不用接口测试冒充页面测试。
6. 全量回归与真实联合运行：逐项记录需求→实现→用例→运行ID；更新交付说明和已知限制，不在未验收时把全量状态改完成。

每批运行相关 Pytest、现有 Node harness、JS语法及差异检查；真实API调用使用已有服务端密钥配置，不写入代码。数据库新增字段采用显式幂等迁移并备份，不假定 create_all 能修改旧表。部署前先验证本地，发布失败保留旧版本和数据备份。
