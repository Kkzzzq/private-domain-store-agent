# 私域电商智能运营平台 PRD

版本：1.0；编写日期：2026-10-14；目标：完成现有项目的双端智能助手与简历所述业务闭环。简历中的 2026-01～2026-05 是项目经历时间，不作为本次开发或测试的事实记录。

## 1. 产品目标与现状

商家通过管理后台维护店铺、商品、SKU、库存与订单，买家通过店铺分享链接浏览、加购、下单、查询订单。双方均能使用中文智能助手，在自己的业务权限内查询实时数据和知识文档。助手回答必须有业务工具或知识片段依据。

已有商品交易、商家装修、认证、订单权限、买家助手、LangChain/Ollama 工具循环、Chroma 检索和 Redis 会话。待补齐商家助手、推荐、可观测的意图识别、结构化分块、上下文压缩、审计、限流及测试。此前的 `prd-agent-enhancement.md` 为历史方案，双端范围与验收以本文为准。

## 2. 用户与权限

- 买家：登录后使用所在店铺助手；只查本店在售商品和公开库存，只查本人在本店订单。另一用户、另一店铺、不存在的订单统一回复“没有找到这个订单”。
- 商家：登录后使用后台助手；店铺由登录身份在服务器解析。可查自己店铺全部商品（含下架）、SKU 库存、本店所有订单、销量与待发货概览。订单回答不包含收货地址、电话等个人信息。
- 未登录用户：可浏览公开商品；助手要求登录。买家不能调用商家接口，商家不能伪装买家调用买家助手。
- 模型不得提供 user_id、shop_id、role、数据库语句或任意接口地址。会话按用户、店铺隔离，不能通过猜测会话 ID 获取他人历史。

## 3. 买家功能与交互

1. 商品咨询：输入名称或品类，返回本店在售商品、价格、规格和库存；商品卡点击进入详情。
2. 库存追问：已有 SKU 编号时精确查询；未指定商品时先追问；“它还有货吗”等追问结合最近商品查询。
3. 推荐：支持热销、浏览偏好、相似商品和预算内推荐，最多 10 件；无浏览记录时返回本店热销；不展示下架、禁售、关闭店铺或无可售 SKU 的商品。预算依据最低可售 SKU 价格，不承诺所有规格都在预算内。
4. 订单：支持具体订单号与最近 5 单；“这个订单发货了吗”继承最近已确认订单号；状态来自业务数据库。
5. 售后与养护：检索平台规则、售后政策、商品说明，展示来源与标题路径；未找到依据时说明并建议联系商家。
6. 对话：显示等待、成功、错误与降级提示；支持新对话；请求中禁用发送，失败允许重试；页面内保留历史。

## 4. 商家功能与交互

后台增加“智能助手”入口，可问“本店订单”“库存预警”“经营概览”“搜索抱枕”“推荐热销商品”“退货政策”。查询订单只限本店，返回订单号、金额、状态、商品摘要；经营概览列出商品数、订单数、已支付销售额和待发货单数；库存预警列出库存不高于指定阈值的 SKU。推荐结果用于选品和经营参考，不能声称未来收益。

本期助手所有工具只读。发货、退款、调库存、改价格、商品上下架继续使用现有业务页面。用户要求助手执行这些操作时说明需到业务页面完成。避免未经确认的模型写操作，同时保留现有后台业务能力。

## 5. Agent 流程

认证 → 解析店铺/身份 → 限流 → 加载会话 → 压缩上下文 → 意图识别 → 按身份选择工具 → 参数校验 → 执行只读工具 → 记录审计 → 输出回答/商品卡/来源 → 保存会话。

明确的订单、库存、政策、推荐、经营查询优先规则识别；其他输入由支持工具调用的模型选择工具。响应暴露意图与实际模式，工具白名单在执行侧再次校验，不能只依赖提示词。Function Calling 经 LangChain `bind_tools` 与 `ToolMessage` 完成，设置最大步骤和每轮工具数。

模型或向量服务不可用时使用规则回答和关键词检索，明确 mode=fallback，不能把降级演示说成真实模型运行。缺参数请求补充；工具暂时失败最多重试一次；返回稳定错误，不暴露内部堆栈和数据库异常。

## 6. RAG 与上下文

知识库本期使用版本管理的公共 Markdown 文档；适用于所有店铺的规则必须在内容中明确说明。店铺实时商品说明和通知由本店业务工具读取，不能将某店私有文档写入公共向量集合。商家可触发公共知识库重建，但不提供私有文件上传。

清洗去除 HTML 注释、规范空白、重复正文段落；按 Markdown 标题组织分块，长块再重叠切分，每块保存 source、heading_path。Chroma 保存 Ollama Embedding，召回内容附来源。重建先完成向量生成，失败保留已有集合。

Redis 会话 TTL 为 7 天；生产用 Redis，开发缺服务时内存降级并报告健康状态。上下文同时计入摘要和消息长度，保留最近完整问答，老消息可经 LLM 摘要，失败使用有界事实摘要，优先保留订单号及最近商品问题。超长单轮不得突破配置预算。

## 7. 安全、审计与接口

- `POST /api/v1/c/shops/{code}/chat`、`GET /api/v1/c/shops/{code}/sessions/{id}`：买家认证。
- `POST /api/v1/b/chat`、`GET /api/v1/b/sessions/{id}`：商家认证，本店解析。
- 响应含 session_id、answer、mode、intent、tools、notices、products；商品卡不包含内部或其他店数据。
- 空白消息 422；超频 429，默认同一用户每分钟 30 请求，Redis 原子计数，降级时进程内计数；请求长度最多 1000 字符。
- 工具日志存用户、店铺、会话、工具、成功标记、耗时和安全标记，不保存完整用户消息、地址、电话或原始任意参数；订单号脱敏。查询被拒与未知工具也要记录。
- 前端使用文本节点展示模型内容，不执行模型输出的 HTML。工具参数禁止额外身份字段。

## 8. 基础设施与交付

Python/FastAPI/SQLAlchemy 实现业务；Docker Compose 提供 MySQL、Redis；Ollama 在宿主机提供聊天与 Embedding 模型；Chroma 持久化。SQLite 与内存 Redis 用于无外部依赖测试，不等同于生产验收。部署说明必须区分这两种方式。

Wireshark 用于本地回环或 Docker 网络的 HTTP/TCP 排障，记录过滤器与可复现步骤，不虚构抓包截图、时延数据或历史排障案例。

## 9. 验收标准

1. 两端均有可使用的助手入口；真实商品、库存、订单与业务页面一致。
2. 买家查询他人订单/其他店铺订单不得泄漏；商家可查本店买家订单，不能查别店订单；模型额外身份参数被拒绝。
3. 四类推荐有效，预算不超最低在售价格；跨店、下架、禁售商品不可出现在买家结果。
4. 同一会话订单追问能继承订单号；长对话压缩后仍保留近期业务事实；相同会话 ID 在不同用户下隔离。
5. 知识块有来源和标题路径，重复段落不会重复写入；模型/向量离线时有明确降级；不能把平台示例政策套成商家承诺。
6. 工具参数校验、未知工具、越权、重试、工具步数限制均有 Pytest 覆盖；限流返回 429；日志脱敏且不影响业务事务。
7. 全部现有 Pytest 回归通过；记录模型工具循环的模拟测试与真实 Ollama/MySQL/Redis 验证之间的区别。
