# 商品数据结构

本次保留 `products` 物理表名，逻辑上作为 SPU 主表，避免为了改名影响订单、评价、栏目等已有外键。

## SPU：products

每行一件商品。`id` 是内部整数主键；`spu_id` 是唯一字符串业务编号。
保存 `shop_id`、名称、分类、描述、主图、状态、排序、销量、限购、创建与修改时间。
状态统一为 `draft`（草稿）、`on`（上架）、`off`（下架）、`banned`（平台禁售），没有独立草稿表。
B 端和 OP 端的商品信息直接来自此表，规格信息来自 SKU 表。

## SKU：skus

每行一个规格。`id` 是规格主键，`spu_id` 为整数外键，指向 `products.id`。
注意：SKU 的 `spu_id` 关联内部主键，并非 SPU 表里的字符串业务编号。
保存规格名、规格图、售价、划线价、库存、状态、排序和修改时间。
同一 SPU 下规格名唯一；参数明细仍保存在 `sku_parameter_profiles`，与 SKU 一对一。

## C 端商品宽表：c_product_views

每个非草稿 SPU 一行。`spu_id` 为主键并指向 `products.id`；`spu_no` 复制字符串业务编号。
独立列保存店铺、名称、分类、状态、是否进入在售目录、最低价（分）、销量、排序，供筛选排序使用。
`payload` 保存完整商品展示内容：主图、说明、限购、标签、评分统计，以及规格的价格、库存、图片和参数。
`source_version` 和 `updated_at` 用于同步检查。宽表可重建，不承担权威库存职责。

草稿不生成宽表行；下架与禁售保留行供浏览记录、购物车标注不可购买。
公开商品目录只返回上架 SPU 和在售规格，店铺营业状态单独实时判断。
商品列表、详情、首页、合集、搜索、推荐、浏览记录、购物车商品内容以及订单当前图片使用宽表。
订单名称、规格、成交价使用下单时保存的订单快照，历史成交记录不跟随商品修改。
店铺、订单、评价、优惠券等各自业务记录仍使用各自的业务表。

## 同步与升级

商品、规格、标签、分类、评分和平台治理写入口刷新相关投影并失效商品缓存。
下单预留、取消/超时回补库存、支付累计销量在同一事务更新对应投影。
读取商品缓存之前会比对 SPU 内容与完整 SKU 内容，发现变更时刷新；启动会重建宽表。
因此展示值来自宽表，但当前同步检查还会查询主表；尚未引入异步消息或 CDC。

启动时为旧 SPU 回填业务编号，将旧 `skus.product_id` 就地改名为 `spu_id`，保留原 ID 与关联。
新建宽表后重建投影。升级不移动草稿、不重建商品 ID、不改订单快照。
数据库备份由现有部署流程执行。此次列改名后，回滚到旧版代码还需恢复旧列名或恢复数据库备份，不能只回滚应用代码。
